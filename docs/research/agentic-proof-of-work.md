## The article's central distinction

**The respondent reports what happened; acceptance depends on the declared checks against exact evidence.** This is not cryptocurrency proof of work, a token-spending score, or a claim that hashing proves software correctness. The sources use “proof of work” for the retained relationship between an obligation, a response, its evidence and the decisions about it. A good article can start with a familiar failure: an agent says the fix works, but its test result and review concern different revisions. The protocol makes that mismatch representable and rejectable. [Hecate's definition][h-ledger], [exact target binding][f-target], [mismatch regression][f-target-tests].

Keep four families distinct, and distinguish the validation requirement from its implementation and result:

| Concept             | What it means                                                                                              | What it does not establish                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Claim               | Directed work with an issuer, respondent, explicit acceptance requirements and declared dependencies       | A chat message, execution launch, or successful result                  |
| Testament           | Respondent-authored immutable account of one work cycle, including its outcome and exact evidence manifest | Automatic acceptance or proof that the claimant received it             |
| Artifact            | Identified, typed, immutable evidence: an output, diagnostic, error or evaluation report                   | A passed check just because bytes exist, are durable, or match a schema |
| Validation          | A declared check of an exact target against a stated requirement/quality bar                               | A mutable status flag or arbitrary executable text                      |
| Validator / verdict | The tool, skill or code implementing the check / its recorded evaluation result                            | Two additional primary object families, or automatic authority to act   |

Local definitions: `../hecate/docs/architecture/LEDGER.md:29–69`; `../focal/CONTEXT.md:7–28`; `../focal/docs/archictecutre/02-domain-and-lifecycle.md:5–7`; `17-lifecycle-state-and-authority.md:57–79`. [Hecate definitions][h-ledger], [Focal terminology][f-context], [peer domain][f-domain], [four-family definitions][f-state].

## Lifecycles: exact enough for prose and diagrams

The four objects do not share a single status. The response's explicit **reported outcome** (`Complete`, `Partial`, `Refused`, `Impossible`, `Interrupted`, `Failed`) is also separate from its evaluated acceptance. None defaults to Complete. A failed or partial report follows the normal response path and includes actual diagnostics; a diagnostic does not fill a missing output slot. [Response contract][f-state], local `17-lifecycle-state-and-authority.md:266–290`; [implemented failure-response test][f-failure-response], local `crates/focal-core/src/native/response_tests.rs:473–515`.

| Object                     | Normal path                                                                                                       | Important branches and guards                                                                                                                                                                                                                |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Claim                      | Generated → Posted → Received → Progressed* → TestamentGenerated → TestamentAcknowledged → Validating → Satisfied | Generated work is durable but not actionable. Progress is observational. Successful local evaluation still waits for declared graph predicates. Cancellation, expiry and other failures have their own terminal facts.                       |
| Work artifact              | Generated → optional Received → Attached → Validating → Validated                                                 | Received here means claimant observation before attachment, not quality. Closing may attach directly from Generated. GenerationFailed, ReceiptFailed and ValidationFailed remain distinct; a failed artifact is not reopened.                |
| Response testament         | Generated → Posted → Received → Validating → Validated                                                            | Generation freezes the manifest and attaches its eligible artifacts atomically. Posting is respondent-owned; receipt is claimant-owned. Terminal response outcomes distinguish ValidationIncomplete, ValidationFailed and ValidationErrored. |
| Evaluation of a validation | Ready → Validating → optional ValidatingQualityBar → Validated                                                    | Agentic-only checks enter their declared quality phase directly. A declared programmatic-plus-quality check needs a real programmatic Pass first. Fail, Incomplete and Error differ; Observe mode remains recorded.                          |

The claim path deliberately has no `TestamentPosted` state: response posting advances the response, not a newly invented claim status. First response generation already advanced the claim to TestamentGenerated. Subsequent eligible responses do not regress the attained claim phase. Local source: `../focal/docs/archictecutre/17-lifecycle-state-and-authority.md:127–184,186–264,313–425`. [Exact transition tables][f-state]. The separation is exercised by `respondent_closes_actual_evidence_then_posts_and_claimant_receives_separately`; it rejects claimant posting and receipt of an unposted response. Local source: `../focal/crates/focal-core/src/native/response_tests.rs:322–459`. [Executable response sequence][f-response-tests].

For precise status references, Focal retains twenty claim names: seven nonterminal (`Generated`, `Posted`, `Received`, `Progressed`, `TestamentGenerated`, `TestamentAcknowledged`, `Validating`) and thirteen terminal (`Satisfied`, `PostFailed`, `ReceiptFailed`, `TestamentGenerationFailed`, `ValidationIncomplete`, `ValidationFailed`, `ValidationErrored`, `Cancelled`, `Expired`, `Revoked`, `Superseded`, `DependencyFailed`, `Deadlocked`). `TestamentGenerationFailed` includes retained historical behavior: the newer contract does not fabricate automatically acknowledged failure testimony for an absent respondent. Invalid generation or failure to commit cannot truthfully manufacture a durable claim transition. Local sources: `02-domain-and-lifecycle.md:220–234`; `17-lifecycle-state-and-authority.md:149–169`. [Vocabulary][f-domain], [historical distinction][f-state]. The article does not need to enumerate all twenty.

**Receipt is intentionally weak.** A pure Required WholeWork Receipt check has no handler, evidence schema or quality bar; it passes on authorized receipt of the exact response, including failure testimony. Every claim declares at least one Required WholeWork receipt check. Receipt-only consultation can therefore finish when an answer arrives without pretending that answer passed a quality review. Local sources: `02-domain-and-lifecycle.md:340–344`; `17-lifecycle-state-and-authority.md:335–341`. [Receipt contract][f-domain], [non-artifact exception][f-state].

## Authority and validator binding

The claimant owns the acceptance requirements. Advisors contribute suggestions/provenance; that does not let them rewrite requirements. Required policy constraints participate in resolution before content freezes. Later changes require explicit successor content, not editing the old obligation. Hecate's role/rank policy is a harness-specific authority arrangement, not a universal requirement for an independent ledger deployment. Local sources: `../hecate/docs/architecture/LEDGER.md:55–60`; `../focal/docs/archictecutre/02-domain-and-lifecycle.md:318–328`. [Provenance][h-ledger], [requirement resolution][f-domain].

The committed requirement pins the check's target, mode, description/quality bar, validator identity/version, evaluator, schemas and bounded attempt/deadline policy. A validator reference is not a mutable endpoint or a deployment instruction. Participants run their own tools and submit results. An issuer may designate itself as evaluator; another peer may evaluate if the requirement designates that peer. Merely consulting a helpful peer does not transfer the original evaluator's verdict authority. No evaluator subclaim is required when the designated participant evaluates directly. Local source: `../focal/docs/archictecutre/16-peer-validation-contract.md:224–283`. [Execution and designation][f-peer]. The descriptor is represented in `crates/focal-model/src/lifecycle/validation_descriptor.rs:29`. [Implemented descriptor][f-descriptor].

**Self-evaluation is not self-targeted work.** Hecate disallows issuing ordinary work to oneself. Although Focal's README contains a self-directed demo, the current authored native posting owner rejects issuer = subject, even when labeled Handoff: it has no authenticated transfer capability to authorize that exception. A representable draft or model-layer Handoff exception is not posting authority. Do not use that README example to collapse claimant and respondent in the article. Local sources: `../hecate/docs/architecture/LEDGER.md:136–137`; `../focal/crates/focal-core/src/native/authored.rs:205–218`; `crates/focal-model/src/lifecycle/claim_descriptor_tests.rs:320–339`. [Inherited restriction][h-ledger], [current posting guard][f-self-target], [model distinction][f-self-draft].

Result admission checks actual authenticated standing and the committed bindings: actor, target, evidence hash, handler version, evaluation generation, attempt, revisions, receipt fence and deadline. The issuer cannot impersonate a different designated evaluator. A generic node identity, context read, or validator name does not grant this authority. Local source: `17-lifecycle-state-and-authority.md:89–116`; `crates/focal-core/src/native/report_tests.rs:1008–1058`. [Authority contract][f-state], [mismatch regression][f-report-authority].

**This is attributable evidence, not automatic independent attestation.** Authentication establishes who submitted the report; a digest establishes which evidence it refers to. Neither proves an arbitrary external program ran honestly. Independent execution proof, an approved evaluator, or extra attestation must be explicitly required. Likewise a validator declaration does not authorize deployment or other side effects; participant permissions and an explicit effect/retry contract still matter. Local source: `16-peer-validation-contract.md:247–266`; `17-lifecycle-state-and-authority.md:413–425`. [Trust boundary][f-peer], [evaluation constraints][f-state].

## Evidence identity, revisions and reuse

Focal separates an opaque typed object ID from a content digest. The contract specifies a versioned canonical BLAKE3 hash over a domain, schema version, namespace, family and immutable body. It excludes the object's own allocated ID and lifecycle fields, but includes referenced stable identities. Moving storage, acquiring a receipt, or advancing status must not make old authored evidence become different content. A claim's authored OccurrenceId distinguishes a retry of the same intention from deliberately repeating otherwise identical work. Local source: `../focal/docs/archictecutre/02-domain-and-lifecycle.md:25–64`. [Identity domains][f-domain].

The native implementation uses family-specific encodings, not one universal byte grammar: artifact content uses BLAKE3 derive-key domain `focal/native/artifact-content/1` with length-framed fields; claim and validation content have separate domains. Artifact identity includes immutable evidence provenance (including its originating receipt), metadata and inline bytes or content reference, but excludes its own allocated ArtifactId. A separate artifact-intent hash includes that ID. Tests verify the same content under a different allocated ID retains its content digest while changing intent identity, and field boundaries cannot collide through simple concatenation. Local sources: `../focal/crates/focal-model/src/lifecycle/artifact_descriptor.rs:528–542,586–719`; `artifact_descriptor_tests.rs:133–246`; `claim_descriptor_hash.rs:4–24`; `validation_descriptor_hash.rs:31–45`. [Native hash implementation][f-native-hash], [identity regression][f-hash-test].

For evaluation, a named slot resolves to exactly one artifact ID and digest within an individual response. Matching a schema does not make artifacts interchangeable. All Required checks for a slot must pass on the **same artifact**. Tests on patch A and review on patch B cannot be assembled into a pass for “the patch.” Source: `17-lifecycle-state-and-authority.md:313–322`; native target and tests: `crates/focal-model/src/lifecycle/validation.rs:74–105`; `validation_tests.rs:1380–1457`. [Same-evidence rule][f-state], [target type][f-target], [rejected substitutions][f-target-tests].

A work artifact has one response attachment. Referencing it later as input neither reattaches it nor reopens its lifecycle. A later response may produce a new artifact with explicit prior-evidence provenance. Reuse of content, context, or a validator definition does not imply reuse of an earlier verdict under a new requirement. No “passed once, trusted everywhere” shortcut is specified. Source: `17-lifecycle-state-and-authority.md:186–190,313–322`; typed nonblocking `DerivedFrom`, `Reviews` and `Refines` relations in `02-domain-and-lifecycle.md:196–214`. [Artifact reuse][f-state], [relation meanings][f-domain].

Schema/custody verification and a substantive verdict are explicitly separate in source tests. The owner rejects a purported Pass paired with error evidence and rejects undeclared evidence schemas even with a verified custody token. Local source: `../focal/crates/focal-core/src/native/report_tests.rs:1063–1107`. [Schema is not a verdict][f-schema-test].

## Failure, retry and partial success

| Situation                                                | Correct interpretation                                                                                         |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Required output absent from the frozen response          | Incomplete: name the missing slot; do not invent an artifact or a hash.                                        |
| Present work demonstrably fails its declared test/rubric | Fail: evidence against that requirement. Do not hunt for a more permissive fallback.                           |
| Validator/tool/reader cannot establish a result          | Error: execution/evaluation problem, not automatically failed work. Retry only within the pinned policy.       |
| Observe check fails                                      | Retain the result and its mode; it neither delays nor fails Required acceptance.                               |
| Agent loses its connection                               | No invented testimony or verdict. Recovery, authorized fencing or a committed deadline supplies the next fact. |
| Corrected evidence arrives after claim terminalization   | New successor/target as permitted; the original terminal status and cause are not overwritten.                 |

Sources: `17-lifecycle-state-and-authority.md:358–425,427–508`; `02-domain-and-lifecycle.md:330–346`. [Outcome contract][f-state], [retry protocol][f-domain]. Implemented tests separately cover Fail/Incomplete/exhausted Error and show that **only Error** advances attempts/fallback handlers; programmatic Pass advances to quality when required. Local sources: `crates/focal-model/src/lifecycle/validation_tests.rs:613–697`; `crates/focal-core/src/native/report_tests.rs:826–899`. [Attempt regression][f-attempt-tests], [owner phase test][f-phase-test]. The Observe/Required test is an admission-check example, not proof that its entire claim is already Satisfied: `report_tests.rs:747–780`. [Observe remains nonblocking][f-observe-test].

There are three different “retry” stories:

1. **Transport retry:** same admitted request identity and same canonical command returns the prior outcome without another effect; changed content under that identity conflicts. This does not establish exactly-once execution of arbitrary participant-side external effects. [Request rules][f-domain], local `02-domain-and-lifecycle.md:287–312`; [implemented request conflict][f-retry-test], local `report_tests.rs:784–822`.
2. **Evaluation attempt:** an Error can advance the bounded, predeclared fallback/attempt chain on the same pinned target. A successful or conclusively failed result is not silently replaced. [Attempt rules][f-attempt-tests].
3. **New work/correction:** explicit response-cycle or successor lineage preserves the previous report and evidence. It is not resetting a terminal check to Ready. [Response cycles][f-state], local `17-lifecycle-state-and-authority.md:292–310`.

Partial work is retained, not rounded up to “done.” The newer profile permits bounded explicit response cycles, each with its own immutable manifest. Before a claim fails, aggregation considers already Posted, Received and evaluated alternative witnesses. A previously valid alternative can cover a required slot; a failed response remains failed even when another response permits the claim to succeed. Every Required check for a slot still belongs to one artifact. A response arriving **after** the first committed uncovered failure cannot heal the terminal claim. Local source: `17-lifecycle-state-and-authority.md:427–464`. [Aggregation and causal cut][f-state]. A mixed-failure owner test retains successful work, failed-slot references and later responses independently: `crates/focal-core/src/native/work_failure_tests.rs:817–876`. [Partial response retention][f-partial-test].

Executable aggregation tests sharpen that boundary: complementary Pass/Fail results across two artifacts do not combine for one slot; different slots may use valid witnesses from different eligible responses; later success cannot heal the first terminal failure. Local source: `../focal/crates/focal-model/src/lifecycle/aggregation_tests.rs:244–349,419–521`. [Same-artifact checks][f-aggregation], [cross-response slot witnesses][f-alternatives], [terminal failure stays terminal][f-no-healing].

## Nesting, dependency graphs and audit closure

Nested work needs explicit relations, not indentation in a conversation. `CausedBy` records an acyclic cause tree. `DependsOn` requires the other claim to be satisfied and propagates failure. `Awaits` waits for terminality and can continue with a failed answer. Review/refinement/derivation relations do not silently become blocking dependencies. Legal dependency cycles are evaluated as a least fixpoint; two claims cannot bootstrap each other into acceptance by each assuming the other succeeded. Local sources: `../hecate/docs/architecture/LEDGER.md:149–171`; `../focal/docs/archictecutre/02-domain-and-lifecycle.md:196–214,356–372`. [Inherited graph law][h-ledger], [precise predicates][f-domain].

```text
satisfied(v) = successful_local_evaluation(v)
               AND every DependsOn target is satisfied
               AND every Awaits target is terminal
```

An owned scope can remain open after its claim becomes terminal. Parent responsibility for registered child work and runtime waits does not disappear because the parent failed. Monitor release means its predicates actually settled; cancellation ends a wait without asserting success or cancelling its targets. Owner release requires a terminal owner, disposed monitors and released child scopes. Local sources: `../focal/CONTEXT.md:30–53`; `02-domain-and-lifecycle.md:374–399`. [Scope vocabulary][f-context], [release contract][f-domain]. CLI tests verify authorized parent-child creation and cancellation propagation: `crates/focal-node/tests/cli_native_children.rs:253–411`; graph tests distinguish DependsOn failure from Awaits: `crates/focal-model/src/lifecycle/graph_tests.rs:163–189`. [Nested CLI workflow][f-child-test], [dependency test][f-graph-test].

The owner-release test constructs a cancelled tree whose claims are terminal but unreleased, rejects premature parent release, then releases leaf → middle → root without changing business outcomes. Local source: `../focal/crates/focal-core/src/native/scope_release_tests.rs:167–217`. [Terminal is not released][f-scope-test].

Audit evidence does not create an infinite “who validates the validator?” recursion. An evaluator's result artifact terminates at Generated; the claimant's result testament freezes and posts an audit bundle and terminates at Posted. These roles do not replace the respondent's testament or reenter ordinary claim acceptance. Begun checks may finish for audit under their live fences after a business outcome; unbegun suppressed checks retain a suppression reason rather than a fabricated verdict. Audit closure does not delay an already justified business terminal state. Local source: `17-lifecycle-state-and-authority.md:488–552`. [Audit role and closure][f-state].

## Distribution, replication, and recovery

The ledger is a shared authority, not necessarily one physical server. **The ordering boundary is a session:** one session has one authoritative mutation order, one Raft group and a current term-fenced leader. Independent sessions have independent logs and sequences. There is no fleet-wide claim sequence, and ordinary cross-session graph edges or atomic cross-session completion are not supported. Cross-session work requires explicit export/import or coordination claims. Local sources: `../focal/docs/archictecutre/02-domain-and-lifecycle.md:13–21`; `04-storage-and-distribution.md:41–61`. [Session boundary][f-domain], [physical and logical units][f-distribution-units].

This distinction preserves the article's central model: participants submit claims, testaments and verdicts to the session's ledger authority. Replicas transport and retain those same committed facts; they do not become separately authorized participants or independently decide whether a claim passed.

### Sharding and routing

There are three different scaling units; a graphic must identify which one it depicts.

| Unit                            | Exact partition key and authority                                                                                                                                                                                                                                                             | Current qualification                                                                                                                                                                                                                                         |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session directory               | Ordered `NamespaceKey = tenant ID bytes ++ session ID bytes`, 32 bytes, with half-open `[start, end)` delegations. A small deployment root delegates namespace spans to directory partitions, rather than holding a row for every claim.                                                      | Partition split/merge is implemented. At the inspected revision the control partitions still run on the founder as single-voter groups; splitting bounds each partition's state, not that host's total memory.                                                |

A write touching several ranges is still one session mutation. Each range plans its fragment before any root moves; fragments publish together or not at all. Untouched ranges also advance through that log entry. A coherent read pins all required ranges at the same sequence and route epoch. The visible sequence cannot run ahead of the slowest active required range; optional followers do not all have to catch up before every read. One slow required range can therefore stall that session's publication, while unrelated sessions continue. ### Replication and failure domains

A replicated mutation is acknowledged only after the Raft group has durably committed it to a quorum; a normal mutation reply also waits for the complete state prefix to become visible. RAM copies alone do not meet the durability requirement. The WAL's path is `RESERVED → ENCODED → APPENDED → FLUSH_SUBMITTED → FLUSH_CONFIRMED → ACK_ELIGIBLE`; an I/O failure stops acknowledgments that depend on the failed write. A one-voter deployment still performs its required local flush. Local sources: `04-storage-and-distribution.md:121–130,222–252`. [Durable replies][f-durable-replies], [flush and quorum contract][f-quorum-durability]. Executable tests reject an acknowledgment from a follower whose durable write failed and reject an isolated leader's quorum read: `crates/focal-consensus/src/tests.rs:497–555`. [I/O-failure and isolated-leader regressions][f-quorum-tests]. These tests were inspected, not run for this research.

The deployment contract supports regional placement or stronger declared failure tolerance. Three voting replicas in three regions retain a two-voter majority after any one region is lost. Five voters in three regions, placed 2/2/1, also survive any one region's loss. Three voters split 2/1 across two regions cannot survive loss of either region symmetrically. Region-tolerant commitments incur cross-region write latency, and they also require suitably placed evidence bytes. An asynchronous backup can lag and cannot be described as zero-loss synchronous failover. Local source: `04-storage-and-distribution.md:27–32,508–545`. [Global placement contract][f-global-placement]. Focal explicitly supersedes Hecate's older region-local/no-WAN-hot-path deployment restriction here; do not blend the two into one contradictory deployment promise.

The published executable qualification is narrower than that global deployment model. A real-binary test starts three processes over QUIC, expands a one-voter session to three voters, kills and restarts the founder during the placement plan, then verifies a quorum read while one other host is down. It is a **three-process node-failure test**, not evidence of a deployed multi-continent fleet or a WAN fault benchmark. The operator can request node/zone/region failure tolerance, but the placement controller still runs on the founder: founder loss pauses placement execution until it returns. A restarted founder can rejoin as a follower if another voter became leader. This controller limitation is separate from the session's consensus election. Local source: committed `24-placement-execution-and-fleet-control.md:929–990`; `crates/focal-node/tests/placement_binary.rs:202`. [Implemented placement journey and limit][f-placement-qualification], [three-process test][f-placement-test].

### Evidence custody and recovery

Artifact bytes have a separate custody path from the session log. The coordinator seals and verifies the object, obtains a `Durable` answer from **every content copy required by the current placement**, and retains receipts naming the ledger, content root, copy, route epoch and policy revision. A new placement cannot reuse stale-scope receipts. Beginning an artifact evaluation is refused while required copies are missing. The bytes must actually be verified; a transfer request or a manifest alone does not establish custody. **Current limit:** per-copy receipt obligations do not yet independently weigh custody against the placement's promised failure domains. Thus a diagram should show both voter placement and required evidence copies, without claiming that a log quorum alone proves the evidence survives a region loss. Local sources: `04-storage-and-distribution.md:265–292`; `26-custody-archive-retention-and-restore.md:13–78`. [Content durability contract][f-content-durability], [implemented custody and limits][f-custody].

Normal recovery loads a verified checkpoint at one published session prefix and replays its committed suffix. Replay applies the recorded outcomes; it does not rerun validators or infer decisions from the old conversation. A checkpoint becomes usable only after its required roots and manifest are durably installed. Local source: `04-storage-and-distribution.md:400–425`. [Checkpoint and replay contract][f-checkpoint-recovery].

Range movement is also governed by the session log. The ordered stages retain the source, destination, snapshot, barrier and readiness facts before activation. Between the barrier and activation, writes touching that member are fenced; unrelated mutations can continue. A dead destination cannot supply readiness, so activation waits. Current automatic recovery covers recorded crash/restart steps, but automatically resolving a destination that never returns remains open. Local source: `25-parallel-materialization-and-ranges.md:394–460,632–676`. [Range movement and fences][f-range-movement], [dead-destination qualification][f-range-holders].

Disaster restore is distinct from ordinary replica failover. The implemented backup restore verifies all required content, refuses to overwrite an already hosted/registered session, and opens a fresh logical log from the retained prefix. It continues the old incarnation only within the same cluster when all other previous members have been revoked. Otherwise it requires an explicit new-incarnation acknowledgment: the copied history has a new authority lineage and is not permission to run two competing authorities for the same old session. Local sources: `26-custody-archive-retention-and-restore.md:525–583`; `04-storage-and-distribution.md:533–545`. [Implemented restore and authority fencing][f-disaster-restore].

A new record reaches durable copies; one region disconnects; the remaining two preserve the majority and an isolated old leader cannot complete an authoritative read. Distinguish normal quorum failover from restoring a backup. Region names and distances are illustrative placement, not production deployment claims.
3. **Evidence availability alongside log durability.** Track the same immutable artifact root to required content copies. Leave one copy pending and keep the operation ineligible; verification supplies the missing custody fact. This shows why knowing a patch's hash and retaining its ledger record are insufficient to read its bytes after a failure.
4. **A range move with a failure mid-transfer.** Show a source, snapshot/catch-up destination and session-authorized barrier; pause touched-range writes while a destination is unavailable, retain unrelated-session activity, then resume from recorded state and activate the new epoch after readiness. Do not show instantaneous cutover or automatic recovery from a permanently lost destination.
5. **Committed versus visible state.** Advance one session log to sequence 43 while active ranges have processed 43, 43 and 42. Keep the coherent view at 42 until the last required range reaches 43, then publish all affected facts together. A separate session can keep advancing. This illustrates cross-range atomicity without adding an unsupported cross-session transaction.

## Failure detection, liveness extensions, and network coordinates

The liveness implementation is separate from session consensus. Its observations become committed **directory placement facts**, while the session's Raft group retains leadership and mutation authority. It must not be illustrated as an agent receiving more time to finish a claim, or as a suspicion vote electing a new session leader. All source references below are at Focal `626b1b59fa286ba4093e96f481afe38b8b061ede`. The working tree's driver, placement agent and architecture document contain additions that shift line numbers; the cited line numbers were checked against `git show` of the committed versions.

### SWIM, Lifeguard, and settled outcomes

- The driver probes members in shuffled rounds. A failed direct probe is followed by up to three indirect probes. Only previously acknowledged/confirmed members can become suspected. A busy probe lane, no route, or a refusal is **inconclusive**, not proof of death. Sources: committed `docs/archictecutre/24-placement-execution-and-fleet-control.md:572–588`; `crates/focal-node/src/liveness/driver.rs:1123–1159`. [Probe sequence][f-liveness-contract], [inconclusive errors and suspicion guard][f-liveness-probes].
- Lifeguard's **observer-local** score is bounded at 0–8. Probe timeouts, self-refutation and late driver ticks raise it; successful probes and answers lower it. The multiplier is `1 + 0.25 × score`, hence 1–3×. Sources: `crates/focal-node/src/liveness/health.rs:6–40`; committed architecture `24:590–605`. [Health code][f-liveness-health]. Do not describe the target's health as directly extending the observer's timeout.
- Independent confirmations shorten a suspicion from its maximum toward minimum: `max − (max − min) × ln(C+1)/ln(K+1)`. The originator and duplicate confirmers do not count. The start time remains fixed; repeated gossip doesn't restart the timer. A higher-incarnation Alive refutes the old suspicion. Sources: `liveness/suspicion.rs:121–162`; committed `24:590–605`. [Suspicion math][f-liveness-extension], [refutation contract][f-liveness-contract].
- The partition leader commits settled Alive/Dead facts, never Suspect, at most one per tick, checked against enrollment generation and nondecreasing incarnation. Placement planning avoids dead members and healing responds to the committed fact. Death doesn't revoke enrollment. Source: committed `24:634–652`; `placement_agent.rs:942–1007`. [Committed liveness][f-liveness-outcomes]. A temporary suspicion is not immediate replica movement.

### Bounded “late homework” extensions

A suspected host refutes with a new incarnation and, when its own health reaches the configured threshold, sends its **accuser** an extension request. The request names the incarnation, progress witness and overload signal. A new incarnation clears the old suspicion before the new extension is considered. The grant provides a grace window for future failed probes and can extend an existing suspicion deadline; it has no claim-deadline or Raft-authority effect. Source: committed `24:607–622`. [Extension contract][f-liveness-contract].

The witness is the placement agent's completed-tick counter, not claim progress, a validator's progress, or arbitrary user work. The source reports overload when memory use is at least 95% of its limit or available disk falls below required headroom. Source: committed `crates/focal-node/src/placement_agent.rs:907–940`. [Witness and overload source][f-liveness-witness].

`ExtensionTracker::request` permits at most five grants **per member incarnation**, at least one probe period apart, only when the witness advances after a previous grant, and never with reported overload. Grants decay by halving down to a floor, `max(base >> count, min_grant)`. Source: `liveness/suspicion.rs:8,56–81`. [Grant and refusal implementation][f-liveness-extension]. Important numeric distinction: actual defaults use a 1,000 ms floor and a 3,120 ms base derived from the ten-member suspicion calculation, giving **3,120 + 1,560 + 1,000 + 1,000 + 1,000 = 7,680 ms**. The algorithm-test fixture instead uses base 3,000/floor 500, yielding 6,250 ms. Do not present the fixture as the runtime default. Sources: committed `liveness/driver.rs:64–76,1391–1425`; `liveness/algorithm_tests.rs:138–200`. [Runtime timeout configuration][f-probe-config], [fixture's alternate parameters][f-liveness-algorithm-tests]. A per-incarnation bound is not a lifetime bound across arbitrarily many new incarnations.

### Vivaldi deadlines and actual routing

Coordinates contain an eight-dimensional vector, nonnegative access-link height, bounded adjustment, relative error and sample count. Prediction uses Euclidean distance plus both heights and adjustments. Acknowledged RTT observations update the estimate and its error. The upper bound is estimated RTT plus twice an error margin; fewer than three samples or an invalid remote coordinate use defaults `100 + 2 × 50 = 200 ms`. Source: `liveness/coordinates.rs:9,55–98,103–173`. [Coordinate code][f-network-coordinates]. The embedding is a latency model, not physical geography.

The deadline is `clamp(3 × RTT upper bound, 300 ms, 2,000 ms) × local health`, rounded after scaling. Healthy fallback is 600 ms; maximum with a saturated health multiplier is 6,000 ms. Source: committed `liveness/driver.rs:64–76,1391–1405`. [Deadline implementation][f-probe-deadline]. These are current node-local defaults, not tuned/benchmarked optimal values.

**Coordinates do not rank request routes or choose a leader.** The production consumer is the probe timeout. Request resolution reads the directory's session route/cache and uses `SessionRoute.leader` with its current `route_epoch`; probe selection uses shuffled member rounds. Source: `route_cache_host.rs:245–277`. [Actual route resolution][f-liveness-routing]. Raft separately enables `check_quorum` and `pre_vote`; liveness grants cannot authorize a minority commit. Source: `crates/focal-consensus/src/lib.rs:496–507`. [Consensus configuration][f-liveness-raft].

### Qualification and limits

The three-node QUIC test stops a host, observes suspicion and a committed dead fact, restarts it with a higher incarnation and observes committed revival without re-enrollment. Crafted-probe tests check sender binding, refutation, grants, rate limiting and overload refusal; algorithm tests check coordinate convergence, health bounds and capped extension arithmetic. The extension path is **not qualified by an actual overloaded host**, and these tests establish no WAN performance result or guarantee against all liveness flapping. Node-local constants, flat membership and founder-host liveness/control limitations remain explicit. Source: committed `docs/archictecutre/09-implementation-status.md:7262–7313`; `24:654–665`. [Recorded qualification][f-liveness-tests]. Tests were inspected, not run as part of this source review.

Hecate's accepted disk-backed support epochs and candidate fleet-Lifeguard discussion are separate designs; they must not be combined with the implemented SWIM path into an invented leader-lease extension. The article uses the concrete implemented peer detector and retains the independent quorum boundary.

## Practical examples for the article and animations

These are illustrations derived from the contract, not captured executions or copy-pastable schema examples.

**A parser fix tested on the wrong revision.** A claim asks the parser to reject a malformed escape while preserving valid input. Its `change` slot requires both behavior tests and review of that exact patch. The respondent submits patch A and its test result. A review of patch B is not a second vote for A: the target binding differs. The useful visual is two checks joining the same identified artifact, with the mismatched branch remaining separate. This demonstrates why identity matters without implying a hash proves correctness. [Exact targets][f-target-tests].

**A test runner outage.** The patch is present, but the designated test runner cannot start because its dependency is unavailable. Record Error with the diagnostic. A permitted fallback may run against the same target/version. If the test actually ran and found the parser still accepts the malformed escape, record Fail instead; no fallback is allowed merely to obtain a green result. [Bounded attempts][f-attempt-tests], [timeout interpretation][f-state].

**A useful partial response.** A worker supplies the requested analysis but cannot produce a second required output. The testament says Partial and retains both the analysis and real diagnostic. Its presence does not fill the absent slot. If an eligible already-validated alternative covers that slot, aggregation can use it; otherwise the absent required evidence is Incomplete. Do not animate a later green artifact erasing a prior terminal failure. [Partial work][f-partial-test], [alternative witnesses][f-state].

**A consultation that can fail usefully.** An agent asks another peer whether an API assumption is correct. An Awaits edge allows the caller to resume with an answer that disproves the assumption. A different claim whose implementation DependsOn that assumption being established cannot treat the same failed result as a satisfied prerequisite. [Documented graph example][f-domain].

**Research with an explicit quality bar.** A research claim can ask for a comparison supported by primary sources, with an artifact containing findings and citations. A schema check can verify the expected structure; the designated evaluator still judges whether those sources actually support the findings under the declared rubric. A collection of valid URLs is not that judgment. The required programmatic and quality phases remain distinct. [Validator contract][f-peer], [ordered phases][f-attempt-tests].

**A migration with separable obligations.** A parent migration claim can depend on tested transformation work and a separately checked compatibility report. It may also await a consultation whose answer can change the plan. The parent does not become satisfied just because its own summary is complete, and cancellation does not pretend that child cleanup has already happened. These are declared dependencies and ownership rules, not a guarantee that a database migration is safe or reversible. [Graph predicates][f-domain], [owned scope release][f-scope-test].

**A handoff without losing the proof.** The durable record identifies which work is outstanding, which outputs are exact and which checks have already passed; a replacement participant need not treat the old transcript's “done” as authoritative. Receipt adoption and generation fences prevent the old holder from continuing to publish as if nothing changed. Do not promise automatic restart of participant tools: the protocol records and authorizes, while the participant owns execution/reconciliation. [Identity and standing][f-state], [participant execution][f-peer].

## Editorial traps to avoid

- Do not turn the article into “Introducing Focal.” Hecate supplies the architectural origin; Focal supplies precise peer contracts and concrete implementation evidence.
- Do not equate a model's confidence, a Complete report, receipt, schema validation or a hash with acceptance.
- Do not draw requirements appearing only after the worker finishes; the contract pins them before work is accepted.
- Do not claim the ledger launches validators, arbitrates arbitrary human truth, or independently attests external execution.
- Do not suggest every check needs a different agent or a separately deployed worker registry. Roles and exact designation matter; topology is not evidence.
- Do not merge evidence across revisions or schema-compatible artifacts, automatically reuse old verdicts, retry conclusive failure until it passes, or rewrite terminal history.
- Do not label Hecate's detailed test matrices as tests run, or assume stale Focal migration headers describe the current executable state.
- Keep Hecate-specific enforcement policy separate from the general protocol. Focal deliberately changes some inherited restrictions; use its explicit decisions/current tests for a Focal example.
