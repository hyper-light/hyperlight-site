# Source-specific notes for Agentic Proof of Work

Research date: 2026-09-12. Scope: the 42 reference definitions in `content/posts/agentic-proof-of-work.mdx`, and the corresponding popover copy in `lib/proof-reference-notes.ts`.

Primary sources were inspected with read-only `git show` calls against the article’s pinned revisions, not the sibling repositories’ changing working trees:

- Focal: `626b1b59fa286ba4093e96f481afe38b8b061ede`.
- Hecate: `103c0785d2623c19d0c02a450e94677bbfc70359`.

No sibling-repository changes, builds, tests, installations or server runs were performed. Test notes describe assertions in the cited source, not tests executed during this research. Numerical liveness examples below are calculations from the pinned defaults, not performance measurements.

## Editorial boundaries

Each source ID gets its own explanation and title. A lifecycle specification is not interchangeable with a regression test, custody is not quorum replication, and liveness observations are not leadership authority. Each popover remains attached to the article’s original pinned source link; the notes do not replace those links with this research file.

The examples use the existing article’s parser claim. They illustrate the cited rule rather than inventing a runnable Focal command or claiming the linked test uses precisely the article’s names. No existing mini-animation is reused: the quorum miniature illustrates a Slates-specific recovery sequence, not Focal regional placement.

## Evidence by reference

The first column omits the exported `agentic-proof-of-work:` prefix. Paths below preserve Focal’s actual `docs/archictecutre/` spelling.

| Reference                | Specific finding and distinction                                                                                                                                                                                                                     | Primary evidence                                                                                                                                             |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `ledger`                 | The ledger records obligations, responses, evidence, relationships and lifecycle facts; machinery configuration, telemetry and VFS bytes have different owners.                                                                                      | [Hecate LEDGER §§1–2][hecate-ledger], lines 18–107.                                                                                                          |
| `peer`                   | Designated evaluator authority is fixed by the requirement. Consultation supplies advice, not an implicit transfer of the original verdict authority.                                                                                                | [Peer validation contract §§1, 4][peer], lines 17–44 and 224–284.                                                                                            |
| `claim-states`           | Generated is not actionable; posting and execution receipt enable work. Progress has no local-completion effect, and local completion still depends on graph predicates for satisfaction.                                                            | [Lifecycle §3][lifecycle], lines 127–185.                                                                                                                    |
| `object-states`          | Four object families have independent lifecycle writers. Execution, artifact observation and testament receipt are different facts, not aliases for acceptance.                                                                                      | [Lifecycle §§1–6][lifecycle], especially invariants at lines 87–126.                                                                                         |
| `response-states`        | A response’s generated account freezes its outcome, confidence and bindings before posting and receipt. Non-Complete outcomes require real respondent-authored diagnostic evidence; disappearance does not manufacture testimony.                    | [Lifecycle §5][lifecycle], lines 231–312.                                                                                                                    |
| `artifact-identity`      | Content identity is domain-separated BLAKE3 over immutable fields and provenance. Its own ID is excluded from content identity and combined with that hash for intent identity.                                                                      | [Artifact descriptor][artifact], lines 528–535 and 586–708.                                                                                                  |
| `identity-tests`         | The tests explicitly vary the artifact ID without changing content identity, then vary field boundaries (`ab`/`c` versus `a`/`bc`) to reject ambiguous concatenation.                                                                                | [Artifact identity tests][identity-tests], lines 133–205.                                                                                                    |
| `validation-states`      | All Required checks for a slot bind to the same artifact ID and digest. Programmatic-plus-quality requirements require programmatic Pass before quality; agentic-only requirements begin in quality.                                                 | [Lifecycle §6][lifecycle], lines 313–426.                                                                                                                    |
| `aggregation-tests`      | `complementary_artifact_checks_cannot_manufacture_a_slot_pass` constructs opposing pass/fail pairs. The following test rejects wrong IDs and digests rather than accumulating them.                                                                  | [Aggregation tests][aggregation-tests], lines 244–350.                                                                                                       |
| `validator-contract`     | Participants resolve and execute validator implementations outside the ledger. Pinned definitions and authenticated submission do not independently attest that a program executed.                                                                  | [Peer contract §4][peer], lines 224–284.                                                                                                                     |
| `test-report`            | Schema decoding rejects unknown/malformed fields. `failed > 0` wins over passes; `passed == 0` means Incomplete; otherwise Pass. This implementation evaluates counts and does not run tests.                                                        | [TestReportValidator][test-report], lines 175–220.                                                                                                           |
| `aggregation`            | At ordered commit, aggregation considers already posted, received and evaluated successful witnesses for uncovered requirements. Different slots may use different witnesses; terminal history cannot be healed later.                               | [Lifecycle §7][lifecycle], lines 427–509.                                                                                                                    |
| `dependencies`           | Satisfaction requires local success, satisfied DependsOn targets and terminal Awaits targets. The least fixpoint begins false, so dependency cycles cannot bootstrap success.                                                                        | [Domain §7][domain], lines 356–430.                                                                                                                          |
| `scope`                  | Scope ownership can outlast a terminal claim. Wait disposition and recursive child-scope release remain obligations; cancelling a monitor does not assert success or cancel its target.                                                              | [CONTEXT language][context] and [Domain §7][domain].                                                                                                         |
| `request-identity`       | The scoped key includes principal, ledger, request epoch and request ID. Same key plus different command digest conflicts; expired history requires a verified archived receipt or RequestHistoryExpired, never blind re-execution.                  | [Domain request history][domain], lines 287–315.                                                                                                             |
| `audit`                  | Result artifacts stop at Generated and result testaments at Posted. Their explicit audit roles never recursively enter ordinary response acceptance.                                                                                                 | [Lifecycle §8][lifecycle], lines 510–553.                                                                                                                    |
| `distribution-authority` | The root delegates directories; session Raft groups order their own histories. State partitioning is separate from consensus replication and does not add independent session sequencers.                                                            | [Storage §2][storage], lines 41–89.                                                                                                                          |
| `range-movement`         | Movement records Begin, Snapshot, Barrier, SourceSealed, Ready, Activate, Abort and Cleanup in the session log. Between Barrier and Activate, affected writes are refused RangeMoving while unrelated members can proceed.                           | [Ranges §6][ranges], lines 378–458.                                                                                                                          |
| `range-publication`      | Publication is bounded by the minimum applied prefix of required active ranges, subject to installed roots. ReadIndex and one pinned ReadToken prevent mixed-prefix reads and stale-epoch progress publication.                                      | [Storage publication/read contract][storage], lines 298–342.                                                                                                 |
| `session-boundaries`     | A session is the graph consistency boundary. Cross-session work needs explicit coordination or evidence import/export rather than atomic graph edges spanning independent session logs.                                                              | [Domain §1][domain], lines 13–22.                                                                                                                            |
| `durable-commit`         | Normal Committed replies require both quorum commitment and complete-prefix publication. An explicitly named durable-submission receipt can precede materialization but requires a minimum-sequence read contract.                                   | [Storage §3][storage], lines 94–130.                                                                                                                         |
| `quorum-tests`           | A follower’s injected persistence error cannot supply an acknowledgment to commit. The neighboring isolated-leader test also prevents local ticking/disk state from completing a ReadIndex quorum barrier.                                           | [Consensus tests][quorum-tests], lines 497–557.                                                                                                              |
| `global-placement`       | Three voters placed 1/1/1 across regions survive any one-region loss; 2/1 across two regions cannot survive loss of the two-voter region. These are quorum arithmetic and placement requirements, not WAN latency measurements.                      | [Storage global placement][storage], lines 508–552.                                                                                                          |
| `content-custody`        | Durable copy acknowledgment follows complete-object verification. Custody receipts bind copy, object, route epoch and policy revision; evaluation eligibility checks current required-copy obligations.                                              | [Custody §1][custody], lines 13–71.                                                                                                                          |
| `failover-authority`     | Linearizable serving requires current ReadIndex authority and complete published roots. Publication progress is bound to term and route epoch; election alone does not make a replica read-ready.                                                    | [Storage ownership and reads][storage], lines 57–64 and 315–342.                                                                                             |
| `checkpoint-recovery`    | The checkpoint manifest names every required range/content root at one prefix. Recovery verifies this state, replays committed suffix records and rebuilds indexes; validators are not rerun.                                                        | [Storage checkpoint contract][storage], lines 400–460.                                                                                                       |
| `disaster-recovery`      | Same-incarnation restore requires the same cluster and revocation of every other old member’s enrollment. Otherwise the explicit `--new-incarnation` acknowledgment creates another log identity and activation genesis.                             | [Custody restore contract][custody], lines 525–583.                                                                                                          |
| `placement-tests`        | A real three-process QUIC qualification expands voters, restarts the killed controller during the plan, reaches activation, then reads with one host stopped. No geographically distributed latency result follows from this test.                   | [Placement §17 qualification][placement], lines 929–977.                                                                                                     |
| `range-limits`           | Current voters and extra holders still materialize the whole session; extra range-serving holders distribute reads, not per-holder session memory.                                                                                                   | [Ranges open issues][ranges], lines 673–678, and §6 lines 378–392.                                                                                           |
| `control-limits`         | One-voter partition groups remain on the founder, so partitioning bounds each owner’s metadata but not the founder’s aggregate state or host dependency.                                                                                             | [Placement §13 limits][placement], lines 763–770. Do not repeat this older paragraph’s “no route cache” claim: §14 immediately documents its implementation. |
| `custody-limits`         | The current obligation verifies required copies without independently weighing them against the promised failure domains. Copy possession alone is not a regional-survival proof.                                                                    | [Custody §1 limits][custody], lines 72–79.                                                                                                                   |
| `liveness-probes`        | Direct and indirect failure can start suspicion only for confirmed members. Busy/no-route/refusal outcomes are inconclusive; they do not prove the peer died.                                                                                        | [Probe driver][driver], lines 1123–1175.                                                                                                                     |
| `liveness-health`        | The score saturates at 8; timeouts scale by `1 + 0.25 × score`. Local probe failures, late ticks and required self-refutations increase it; successful probes/answers decrease it.                                                                   | [LocalHealth][health], lines 1–44.                                                                                                                           |
| `liveness-contract`      | Independent confirmations shorten the existing suspicion deadline; repeated evidence does not restart it. Higher-incarnation Alive refutes stale suspicion.                                                                                          | [Placement Lifeguard contract][placement], lines 590–606.                                                                                                    |
| `liveness-extensions`    | The request refuses overload, no progress, too-short interval and exhausted allowance. Maximum five extensions; each is `max(min_grant, base >> count)`.                                                                                             | [ExtensionTracker][extensions], lines 8–99.                                                                                                                  |
| `liveness-witness`       | Placement-loop tick count supplies the progress witness. Overload is memory at least 95% of limit or free disk below headroom; it is not claim completion.                                                                                           | [Placement agent facts][witness], lines 907–945.                                                                                                             |
| `network-coordinates`    | Coordinates carry an eight-dimensional vector, access-link height, adjustment, error and samples. Successful RTT observations update them; invalid or insufficient data uses conservative fallback estimates.                                        | [Vivaldi coordinates][coordinates], lines 1–155 and `rtt_ucb_ms` immediately following.                                                                      |
| `coordinate-deadline`    | Defaults are factor 3, 300 ms base, 2,000 ms cap; multiply the clamped estimate by local health afterward. Thus a 200 ms upper estimate and health 2 give 1,200 ms, and the maximum health-scaled cap is 6 s.                                        | [Probe configuration and deadline][driver], lines 64–79 and 1391–1410; [LocalHealth][health].                                                                |
| `leader-routing`         | Directory-backed cache entries select the session leader and route epoch. Endpoints come from the peer pool, and route-log gaps invalidate a partition’s cache; latency coordinates do not choose writers.                                           | [Route cache host][routing], lines 245–305.                                                                                                                  |
| `committed-liveness`     | Partition leadership commits settled generation/incarnation-checked alive/dead facts, not suspicion. Planning and effective-guarantee checks consume the same facts; enrollment persists through death and revival.                                  | [Placement committed outcomes][placement], lines 634–654.                                                                                                    |
| `raft-authority`         | The consensus adapter enables `check_quorum` and `pre_vote`; liveness grace does not modify session Raft authority or claim deadlines.                                                                                                               | [Consensus configuration][raft], lines 500–512; [Placement detector contract][placement].                                                                    |
| `liveness-tests`         | Real QUIC qualification covers stopped-host death and higher-incarnation revival. Crafted probes cover sender binding, refutation and extension decisions; these do not establish behavior under real sustained overload or measured WAN conditions. | [Implementation qualification][liveness-tests], lines 7262–7310.                                                                                             |
