**Vorpal** is a code-analysis and search engine for people and agents. It finds definitions, follows calls across files, matches code by its syntax, and searches for the code behind a description. It runs locally, ships as one Rust binary, and works through the CLI or MCP. [The source is open.][repo]

Agents spend too much time figuring out where things are - taking dozens of tool calls to figure out who calls a function, read the matches for type definitions, work out architecture and dependency relationships, and follow imports. Ask the next question and much of that work starts again. On smaller repositories it means minutes or hours of time wasted. On large repositories it means massive inference bills, broken or incomplete patches, and developer frustration.

Vorpal combines a trigram text index with Tree-sitter parsing and a stored knowledge graph. A separate vector index uses exact search for smaller sets and Vamana for larger ones. Together, these let it narrow text searches, match code by structure, and follow resolved relationships. Vorpal supports 49 Tree-sitter grammars, compiled into its single binary, and offers ast-grep's substitution and rule capabilities for editing and linting.

## Answering a question

Download the [binary for your platform][releases]. There is no archive to unpack and no Node.js or Rust toolchain to install.

On macOS with Apple Silicon:

```sh
mkdir -p "$HOME/.local/bin"
curl -fL https://github.com/hyper-light/vorpal/releases/latest/download/vorpal-macos-arm64 \
  -o "$HOME/.local/bin/vorpal"
chmod +x "$HOME/.local/bin/vorpal"
export PATH="$HOME/.local/bin:$PATH"
vorpal --help
```

The `export` makes Vorpal available in this shell. Add `~/.local/bin` to your shell's `PATH` if you want it available in new terminals too. Intel macOS, Linux, and Windows binaries are on the same [releases page][releases].

Then try it on Vorpal itself:

```sh
git clone https://github.com/hyper-light/vorpal.git
cd vorpal

vorpal index .

vorpal graph callers resolve_import_path \
  --path crates/resolve/src/resolver.rs \
  --format json

vorpal graph implementors FileExtractor
vorpal search "stat manifest change detection" -k 5 --format json
```

The first query finds callers of `resolve_import_path`. The path selects the definition in `resolver.rs`, since more than one file can define the same name. The second finds implementations of `FileExtractor`. The third searches for code that detects file changes, without requiring you to know what that code is called.

The README's captured results include `resolve`, `OutlineExtractor`, and `FileStat`, respectively. This is Vorpal searching its own code. [CLI setup and examples.][getting-started]

`vorpal index .` writes to `./.vorpal/index`. Queries read that location relative to your current directory. If you index a different directory, pass its index path with `--index`.

## Why Tree-sitter matters

Consider these two pieces of C:

```c
void *buffer = kmalloc(
    requested_size,
    GFP_KERNEL
);

const char *example = "kmalloc(requested_size, GFP_KERNEL)";
```

The first calls `kmalloc`. The second is a string. Searching for a call should match the first and skip the second, regardless of line breaks.

[Tree-sitter][tree-sitter] parses a file into a concrete syntax tree. Each node identifies a piece of syntax and where it occurs in the source: a function definition, a call, an argument, a string, a comment. It also handles incomplete syntax, so useful analysis can continue while you are editing a file that does not compile yet.

Vorpal builds on [ast-grep][ast-grep] for structural matching and rewriting. For example, from a C repository:

```sh
vorpal run -l c \
  -p 'void example(void) { kmalloc($A, $B); }' \
  --selector call_expression .
```

`$A` and `$B` match the two argument expressions. The surrounding function tells the C parser that this is a call; `--selector call_expression` selects just the call as the pattern. Keep it single-quoted so your shell does not expand `$A` and `$B`.

Tree-sitter tells us where a call is and what it looks like. Finding the definition it calls is a separate problem. That requires scope, imports, and often type information. Vorpal's resolver does that work after extraction.

## How it works

There are four main steps: extract definitions and references from files, resolve those references, store the graph, and build the indexes used by queries. When a file changes, Vorpal reuses the work it can and updates the affected relationships.

<VorpalArchitecture description="Files pass through Tree-sitter and reference resolution into a stored graph. CLI and MCP queries use the graph and search indexes. File changes update the affected data." />

### Extract facts once

The indexer finds supported files and checks which have changed. For each changed file, Tree-sitter parses the source. Language-specific rules extract definitions, and a tree walk collects references, calls, imports, and type information. Vorpal caches those results per file so the next index build can reuse them.

Files are processed in parallel, with limits on queued work and temporary memory. The finished graph still grows with the repository; limiting parsing work does not make millions of nodes free to store. [Indexer implementation.][ingest]

### Resolve across files

Two functions called `save` are not necessarily the same function. The resolver checks where a name is used, what that file imports, which definitions are visible, and what can be established about the receiver's type.

Results include a grade: `exact`, `constrained`, `heuristic`, or `unresolved`. Those grades distinguish a proven binding from a likely match. You can inspect the evidence behind a relationship and see what could not be resolved. [Resolver implementation.][resolver]

Support differs by language. Having a parser does not mean every relationship in that language is implemented. The [language matrix][languages] lists what Vorpal extracts and resolves.

### Store the graph

Vorpal assigns nodes compact integer IDs and stores their fields in columns. It memory-maps the stored data so queries can read it without first copying the entire index into application memory. Stable external IDs are derived from the file path and entity path using BLAKE3; the smaller internal IDs are used for lookups within an index generation.

Edges are indexed in both directions. If `A` calls `B`, we want to find both what `A` calls and who calls `B` quickly. Without the reverse index, finding callers could require checking every outgoing edge.

The graph uses compressed sparse row storage. Each node has an offset into a flat array of targets:

```text
neighbors(v) = targets[offsets[v] : offsets[v + 1]]
```

Once we have the node, reading its neighbors takes work proportional to the number of edges attached to it. We do not scan the source files. Following calls transitively visits more nodes and edges, up to `O(V + E)` if the traversal covers the whole graph. Reading evidence and serializing the answer add to that query cost. [Graph storage.][graph-storage]

### Update without mixing old and new data

On disk, extraction results and graph data are grouped into buckets. An update can hard-link unchanged buckets into the next version of the index instead of rewriting them. Each version is called a generation and has a content-derived ID.

The new generation is written before `CURRENT` is atomically changed to point to it. A reader gets the old generation or the new one, rather than half of each. MCP answers include the generation they used. Additional search indexes are checked against the data they belong to; if one is stale, Vorpal falls back to a slower query or reports that the feature is unavailable. [Index format.][index-format]

## Why run a server?

A cached syntax tree saves parsing time. It does not automatically save the work of walking the tree, resolving a name, or collecting its callers. If you repeat those steps for every question, you still pay for them every time.

Vorpal stores the resolved relationships and the indexes needed to query them. Even a one-shot CLI query reads that stored index rather than parsing the repository again. The server goes further: it keeps the index loaded across requests, watches for file changes, and updates it while you work.

The MCP client runs the server locally and talks to it over standard input and output. There is nothing to deploy.

We can break the cost down like this:

```text
Repeated analysis ≈ Q × (P + A)
Parse cache       ≈ P + Q × A + U_cache
Persistent index  ≈ I + W + Q × (L + q) + U_index
```

`Q` is the number of questions. `P` is parsing, and `A` is the remaining analysis needed for each answer. For the stored index, `I` is the initial build, `W` is warm-up, `L` is request overhead, and `q` is the query itself. `U_cache` and `U_index` cover updates as files change.

This is a simplified model of repeated code analysis. A cache that also stores resolved relationships removes more of `A`; a literal grep does not need parsing at all. The important difference is where the work happens. An index pays more up front to make each later question cheaper.

### Reuse work inside large files

For files over 1 MiB, the running server can retain the Tree-sitter tree and reuse its unchanged parts after an edit. For C, it can also reuse extraction results outside the edited definition. That makes a substantial difference for generated files:

| Per-save workload                           | Fresh parse + extraction | Incremental parse + walk splice |
| ------------------------------------------- | -----------------------: | ------------------------------: |
| 54 MB generated C, edit between definitions |                    4.2 s |                           0.7 s |
| Same file, edit inside its 43 MB definition |                    4.2 s |                           1.7 s |
| 1.4 MB CPython `Parser/parser.c`            |                   107 ms |                           17 ms |

Editing inside the 43 MB definition costs more because that whole definition must be walked again. The cached source and extraction snapshots have a default 256 MiB budget; retained syntax trees use additional memory. Extraction reuse currently ships for C and falls back to a full walk if its checks fail. Each benchmark result was checked against full re-extraction. [Incremental parsing benchmarks.][performance]

Indexed structural search avoids work too. A trigram index checks which files could contain the literal text in a pattern. Within a file, recorded statement boundaries can narrow what needs parsing. Repeating the pattern reuses unchanged results. Some simple call patterns need no new parse: the index already records calls and their argument counts. When a shortcut cannot preserve the result, Vorpal uses the full parse. [Structural search.][structural-performance]

## How search ranks results

Graph queries work well when you know the symbol. Search is for when you do not.

By default, Vorpal builds several ranked lists. One matches names and name tokens. Another compares **256-dimensional vectors** built by hashing words from names, signatures, and file basenames, then normalizing the vectors. A third takes the name matches and orders them by how many references point to them. When name matching and BM25 return nothing, a body-text search can supply more results. [Search implementation][search-source] and [vector generation.][embedder]

This default vector search is lexical: it compares words found in code. The neural encoder is optional.

<VorpalEmbeddings />

The default embedder splits identifiers at punctuation and camel-case boundaries, then lowercases the tokens. Each token contributes to two signed hash buckets. L2 normalization gives the resulting vector unit length, so repeating every word does not simply make the vector larger. The lexical view above computes the actual buckets for `resolve import path`. [Lexical embedder.][embedder]

The **learned tier** changes how those vectors are built. It learns from words and three-to-six-character fragments that occur together in the repository's definitions. Positive pointwise mutual information, or PPMI, measures associations between them; a truncated singular value decomposition, or SVD, turns that matrix into a smaller set of dimensions. The model removes dominant directions and uses weighted pooling so common tokens do not overwhelm the rest. The corpus determines the dimension, up to 256. Stored document vectors can also be refined using confidence-graded graph relationships. This is a corpus-trained embedder, not the neural reranker. [Learned embedding implementation.][learned-embedder]

The **neural encoder** uses CodeRankEmbed to produce 768-dimensional vectors. It takes the contextual output for the CLS token and L2-normalizes it. Queries get the prefix `Represent this query for searching relevant code: `. Document inputs differ: the background embedding index can include a leading comment and the first paragraph of a definition's source, while the reranker uses a shorter name/signature/basename description. This adds information the lexical channels do not have. [Encoder][neural-embedder] and [document input construction.][search-source]

The code graph and the nearest-neighbor graph have different jobs. The code graph records calls, imports, and other program relationships. Vamana connects nearby vectors to help find candidates. The neural document index uses its own quantized scan and rescoring path; it is not another name for either graph.

The scores from these lists are not directly comparable. A vector distance and a count of references measure different things. Vorpal combines ranks instead, using reciprocal rank fusion:

```text
RRF(d) = Σ [1 / (60 + rank_c(d))]
         c where channel c returned d
```

Vorpal uses **zero-based ranks**. First place contributes `1/60`; absence from a list contributes nothing. A definition ranked first in one list and sixth in another receives `1/60 + 1/65 ≈ 0.03205`. One that appears only first in a single list receives about `0.01667`. Appearing near the top of several lists helps. Each result keeps its ranks so you can see how it was scored. This is the base formula; optional dense-search settings can change a list's weight. [Fusion implementation.][fusion]

<VorpalRanking />

You can enable the corpus-trained embedder, or add a local CodeRankEmbed neural encoder. The neural reranker preserves the fused top result and reorders the remaining retrieved candidates. It cannot add an answer that was never retrieved; the separate background embedding index supplies that additional search path. The encoder requires a download and adds memory and query cost.

The README's encoder results improve on CPython and Vorpal's repository, but score lower on the kernel. Those quality tables were measured before background embedding fill, with default and optional tiers measured on different days. The choice depends on the repository and the questions you ask.

To test your own queries, put one `query => expected-name-or-path` pair per line in a file, then run:

```sh
vorpal tune --queries my-queries.txt
```

Vorpal compares the configurations and enables a tier only when it passes the measured improvement checks. Without expected answers, the command shows comparisons but does not change the settings. [Ranking tiers and evaluation.][search-quality]

## The benchmarks

On the Linux kernel, Vorpal builds an 8.89-million-node graph in **8.1 seconds**. codebase-memory-mcp takes **296 seconds** on the same checkout. Vorpal uses about a fifth of the peak memory and less than a third of the disk space. Once the index is current, a warm graph query takes **0.13 milliseconds**.

Those are different parts of the job. Building the index, keeping it current, answering a query, and getting an agent to finish a task each deserve their own measurements.

The results below come from the [README benchmarks][readme], run on an Apple M5 Max with 18 cores and 128 GB RAM, macOS 26.4.1, and rustc 1.98.0. The main indexing and competitor comparisons used v0.9.0 on September 7, 2026. The broader language and optional-tier results include September 5–6 runs; the agent experiments use v0.8.3 and are dated separately below.

The kernel checkout is `1590cf032971`, CPython is `b86a41cbf63`, and the other repositories have pinned commits in the README. CLI timings include process startup. Vorpal's cold indexing times are the best of three runs after checking that the machine was quiet. “Cold” means building a new index, not flushing the operating system's file cache. The tgrep build times are medians of three; daemon query times are client-side round trips.

### Finding the right result

Speed is only useful if the right code comes back. The labeled sets contain 54 kernel queries, 54 CPython queries, and 55 Vorpal queries, spanning six query classes from exact names to paraphrases. Relevance labels cite source lines so the expected answers can be inspected.

One metric is normalized discounted cumulative gain, or NDCG:

```text
DCG@10  = Σ (2^g_i − 1) / log2(i + 1), for i = 1 … 10
NDCG@10 = DCG@10 / ideal_DCG@10
```

`g_i` is the relevance grade of the result at position `i`, starting at one. A more relevant answer earns more credit, and putting it further down the list reduces that credit. Dividing by the best possible ordering of the labeled answers gives a score between zero and one. The table averages that score across queries; it is a ranking score, not a percentage of questions answered correctly. [Evaluator.][evaluation]

The README also reports MRR, which measures how high the first relevant result appears, and recall@5, which measures how much of the labeled relevant set appears in the first five results.

<VorpalComparisons kind="retrieval" />

On CPython, the encoder raises NDCG@10 by about **15%** and recall@5 by **28%** relative to the default. On Vorpal's repository, NDCG@10 improves by about **13%**. The kernel is different: the default wins on NDCG and MRR, while the learned tier adds a little recall. That is exactly why `vorpal tune` measures your queries instead of assuming the most expensive configuration is the best one.

The default column was measured on September 7, after body-text candidates were added; learned and encoder columns are from September 6. These quality results precede the encoder's background embedding fill. Descriptive kernel queries and paraphrases remain weak in that state: reranking cannot rescue an answer that never reaches the candidate set. [Retrieval results and labels.][search-quality]

### What an agent saves

Start with the tool's own work, before counting model turns. These September 5 measurements use v0.8.3: one warm daemon request versus the ripgrep-and-read operations behind an agent's built-in tools. Vorpal timings are medians of five requests after an initial call.

| Question | Vorpal | Grep + Read | What comes back |
| --- | ---: | --- | --- |
| Vorpal: callers of `tool_result` | **0.10 ms** | 16 ms | 2 call-site records vs 3 lines |

The graph returns relationships the model can use directly. Grep returns text the model still has to interpret. That distinction matters even when both tools are fast. It also means fewer records do not automatically prove better coverage: the graph can miss relationships, and a large resolved result can be longer than the grep output.

Now include the model. On September 6, we asked Claude Code 2.1.261, running Opus 5 at high effort, four questions through three access paths. Each cell ran four times; these are medians of the last three runs with a warm prompt cache.

<VorpalComparisons kind="agents" />

For the kernel callers question, MCP reduced processed tokens by **51%**, billed cost by **79%**, and wall time by **58%**. The CLI reduced them by **65%, 86%, and 63%**. Those are reductions in the work required to answer the question, not just in the few milliseconds spent looking up a symbol.

Tokens include input and cache reads and writes, but exclude output. In this client, the first MCP tool use requires a separate schema-loading turn. The shell tool is already available, which lets the CLI finish in two turns. Each turn processes the context again; avoiding one changes both token use and cost.

These are warm-cache bills, not a price forecast. The first question after an idle hour incurred an additional measured cache-write cost of $0.09–$0.14 for grep, $0.10–$0.13 for MCP, and $0.17–$0.22 for the shell setup. The prefixes differed in size and in how much was already cached.

The runs also exposed concrete coverage gaps. Grep found two inline helpers in `vfs_read` that were not recorded as graph edges, and a transitive call inside a struct literal that the graph missed. On the Vorpal callers question, grep named the enclosing function correctly in only one of six recorded runs. The graph returned some constrained candidates that the model correctly rejected. Both the result and the evidence behind it matter. [Agent experiments and transcripts.][comparisons]

Across all four questions, using Vorpal reduced the measured wall time. Most of the remaining time was the model itself. That is the point: spend less of the agent's context and time rediscovering the code, and more of it doing the work.

## Using MCP

Add Vorpal to your client's MCP configuration. For clients that use JSON, the entry looks like this; replace the path with your repository's absolute path:

```json
{
  "mcpServers": {
    "vorpal": {
      "command": "vorpal",
      "args": [
        "mcp",
        "--index",
        "/absolute/path/to/project/.vorpal/index",
        "--profile",
        "analysis"
      ]
    }
  }
}
```

The client starts Vorpal. If it cannot find `vorpal` on `PATH`, set `command` to the binary's absolute path. The `analysis` profile gives the agent search and graph tools while leaving out the explicit index tool and the full structural tools. Vorpal still updates its own index as files change.

Keep the `<project>/.vorpal/index` layout for automatic file watching. A custom index location outside that layout needs explicit refreshes. With the default layout, Vorpal builds the index if it is missing. To preview automatic client setup instead, run `vorpal mcp install --dry-run`. [MCP setup.][mcp]

To find callers of `resolve_import_path` in the Vorpal checkout, the agent calls `graph` with these arguments:

```json
{
  "relation": "callers",
  "name": "resolve_import_path",
  "path": "crates/resolve/src/resolver.rs",
  "format": "lean"
}
```

Change `relation` to `callees` to follow calls in the other direction, or to `references` to find uses of the definition.

The answer includes the index generation and matching records. Callers and callees can include the line where the call occurs. If there are more results than fit in one page, `total`, `truncated`, and `nextCursor` tell the agent what remains. Source and evidence tools let it read the code behind a result. [MCP tools.][mcp]

## Try it on your code

Vorpal gives you a stored, searchable model of the code, with the information needed to check its answers. Dynamic calls, macros, and relationships a language's extractor does not support can still leave gaps. A traversal follows the edges Vorpal found; it does not replace tests or a compiler.

Repeatability matters here. The release checks compare independent builds byte-for-byte and check incremental results against fresh builds. Changing a file and rebuilding should lead to the same index as starting from that changed source. [Build checks.][readme]

Install the [CLI][getting-started], point it at a repository, and ask about a function you know. Check its callers. Follow its dependencies. Then connect it to your [MCP client][mcp] and let the agent use the same queries.

The less time it spends rediscovering the codebase, the more time it has to work on it.
